Tests are Vitest files in `__tests__/` and there is **no `test` script**. `exam-logic.test.ts` and `quiz-attempt.test.tsx` are self-contained unit/component tests (jsdom, the attempt API mocked): `npx vitest run __tests__/exam-logic.test.ts __tests__/quiz-attempt.test.tsx`; `vitest.config.ts` only adds the `@/` alias. `attempts-api.test.ts` runs the attempt route handlers against the Firestore emulator (needs Java; it skips itself without `FIRESTORE_EMULATOR_HOST`): `npx firebase emulators:exec --only firestore --project demo-ageno-attempts "npx vitest run __tests__/attempts-api.test.ts"` (port set in `firebase.json`). `admin-api.test.ts` does the same for the admin routes, user deletion and the legacy-question migration (`--project demo-ageno-admin`; the Firebase CLI here is the global `firebase`, not `npx`). `firestore-rules.test.ts` does the same for `firestore.rules` (`--project demo-ageno-rules`, `__tests__/firestore-rules.test.ts`). `quiz-schema.test.ts` and `quiz-editor.test.tsx` (the shared quiz schema; the admin editor, jsdom, API mocked) need no emulator. `access-control.test.ts` (middleware rules, the server-side admin check, production-blocked debug routes, the sign-in redirect helper), `session-route.test.ts` and `session-check.test.ts` (the session routes, Admin SDK mocked) need no emulator. Route handlers that call `after()` need it mocked in tests (see those files and `admin-api.test.ts`). Production Firestore uses REST (`preferRest` in `firebase/admin.ts`); the emulator tests' mocks keep the default gRPC transport, because REST asks Google for credentials even against the emulator. On Windows `emulators:exec` can leave the emulator's `java.exe` running (it then fails with "port taken" next time): stop the `java.exe` whose command line mentions `cloud-firestore-emulator`. The other files are integration tests (single file: `npx vitest run __tests__/auth-api-integration.test.ts`) that hit a running dev server at `localhost:3000` and sign in to real Firebase with placeholder credentials hardcoded in the file, so they won't pass without editing those and starting `npm run dev` first. Manual auth test plans live in `docs/`.

### Environment

`.env*` is gitignored. Server-side code needs `FIREBASE_PROJECT_ID`, `FIREBASE_CLIENT_EMAIL`, `FIREBASE_PRIVATE_KEY` (Admin SDK; `firebase/admin.ts` throws at import time if any are missing). ## Architecture

Next.js 15 App Router, React 19, TypeScript, Tailwind v4, Firebase (Auth + Firestore). Path alias `@/*` maps to the repo root. There is no `src/` directory.

### Route groups don't appear in URLs

`app/(admin)`, `(auth)`, `(quiz)`, `(user)`, `(dev)` are route groups, so admin pages are served at `/dashboard`, `/quizzes`, `/users`, `/quiz-reports` (not `/admin/...`; `/settings` is still gated in the middleware but the page was removed in P7.3). The quiz lobby and exam are `app/(quiz)/q/[id]` at `/q/<quizId>` (the address never contains the access code); `app/(quiz)/[code]` only resolves older `/<ACCESSCODE>` links to `/q/<id>`; `/join` is the quiz list and code-entry page.

### Auth and session flow (spans several files)

1. Client signs in via Firebase Auth (`lib/actions/auth.actions.ts`, wrapped by `contexts/auth-context.tsx`; `hooks/useAuth.ts` layers SWR, profile/MFA actions on top of the context).
2. `lib/actions/session.actions.ts` posts the ID token to `app/api/auth/session/route.ts`, which verifies it once, reads the role from `users/{uid}` while it makes the session cookie, and sets `session` (Firebase session cookie, 14 days, httpOnly), `user_role` (httpOnly hint) and `signed_in=1` (readable hint, proves nothing; without it the client skips `/api/auth/session/check`). Everything else (`lastLoginAt`, a new person's profile, the `role` claim, the activity log) runs in `after()`, never as an un-awaited promise. Sign-in, sign-up and sign-out are logged on the server (`lib/server/activity.ts`), not from the browser. `DELETE` signs out this browser only; `?scope=all` with a Bearer ID token revokes refresh tokens (Profile → Security → Sign out of all devices).
3. `middleware.ts` runs on the edge, so it can only check that the `session` cookie *exists* and read the `user_role` cookie as a hint; it never proves anything. It checks the real admin paths (`/dashboard`, `/quizzes`, `/users`, `/quiz-reports`, `/settings`) first, then an allowlist of public paths (anything under `/q/`, the quiz/attempt/leaderboard API routes, which verify tokens themselves, and old `/<CAPITALS5to10>` quiz links). It also 404s the dev-only pages in production (`lib/dev-routes.ts`) and passes the URL on in an `x-pathname` header.
4. `app/(admin)/layout.tsx` is a **server component** and is the real admin gate: `lib/server/admin-access.ts` verifies the session cookie with Firebase (revocation included) and reads the role the way the Firestore rules do (claim, or `users/{uid}.role`), and redirects anyone else before anything renders. `AdminShell` (client) is only the admin chrome. Roles are in `constants/role.ts`.
5. `app/(user)/layout.tsx` (My quizzes, leaderboard, profile) shows a placeholder while auth resolves and redirects to `/sign-in?redirectTo=<path>` when no one is signed in, on every device. `lib/navigation.ts` `safeRedirectPath` keeps `?redirectTo=` on this site. Starting a quiz attempt needs sign-in (the lobby is open to everyone).
6. `firebase/client.ts` starts Auth with `initializeAuth` and **no popup resolver** (so Google's `gapi` script and iframe don't load on every page); `signInWithPopup` must be given `browserPopupRedirectResolver` (done in `lib/actions/auth.actions.ts`). `auth-context` caches user data in localStorage (`lib/services/session.service.ts`) and refreshes the session every 30 minutes.

### Data layer

**Only a signed-in person's own profile and activity log use Firestore from the browser** (the rules still let admins read `users` and `settings`, but no screen does). Everything a player reads or writes, and every quiz an admin creates, edits or deletes, goes through server routes (Admin SDK, `lib/server/*`), and the browser calls them with `lib/api-client.ts` (`apiRequest`, Bearer ID token) through `lib/quizzes-api.ts` and `lib/exam/api.ts`:
- `GET /api/quizzes` and `GET /api/quizzes/[quizId]`: the public quiz shape (`PublicQuiz` in `lib/quiz-data.ts`: **never the access code**, owner or answer settings) plus question counts (from the quiz's stored `questionCountByDifficulty`). Both, and each level's question set used by `startAttempt`, go through Next's data cache (`lib/server/cache.ts`, tags `quizzes` and `quiz:<id>`); the admin quiz routes call `invalidateQuiz(id)` after every create/save/delete, so **any new code path that writes a quiz or its questions must call it too**. Not CDN-cached (`no-store`). `POST /api/quizzes/resolve`: access code → quiz id (the only place a code becomes a quiz).
- `POST /api/attempts/start` (checks the access code on the server and needs sign-in), `GET`/`PATCH /api/attempts/[id]` (resume, autosave), `POST /api/attempts/[id]/submit`, `GET /api/attempts/[id]/result` (a finished attempt's stored result and review, owner only; shown at `/my-quizzes/<attemptId>` with `ResultsScreen`, the same display as right after a quiz).
- `GET /api/leaderboard` and `GET /api/my-attempts`: one query plus batched name/title lookups each; display names only, never emails.
The browser never sees which option is right until a submit returns the review; see "The quiz-taking flow" below. `firebase/firestore.ts` is now **types only** (`Quiz`, `QuizQuestion`, ...): no runtime code, so the server can import it. `lib/quiz-data.ts` (`quizFromData`) holds the field defaults.
- **Admin routes** (`app/api/admin/*`, guarded by `requireAdmin` in `lib/server/admin-access.ts`; browser calls in `lib/admin-api.ts`): quizzes (list, open with the answer key, create, save in one transaction with a `version` check, delete with results), users (list, change role = `role` claim + profile + sessions revoked on demotion, delete = Auth account + profile), `reports` (paged) and `stats` (aggregations). Logic in `lib/server/admin-quizzes.ts`, `admin-users.ts`, `admin-reports.ts`. **`lib/quiz-schema.ts` is the one description of a quiz** (types, `validateQuizInput` used by editor and server, stored shape, legacy handling); `lib/quiz-writes.ts` plans question writes. `npm run migrate:questions` moves old shared `questions` collections into the per-level ones (dry run unless `-- --apply`).

Questions are stored per difficulty in subcollections `quizzes/{id}/questions_{easy|medium|hard}` (see `firebase/quizDifficulty.ts`), with a fallback to the legacy `quizzes/{id}/questions`. Per-difficulty `difficultySettings` (duration, `pointsMultiplier`) live on the quiz doc; see `docs/DifficultySettings.md` and `utils/difficulty-helpers.ts`. Final score is raw % (of every question in the attempt) times the multiplier (1 when a level sets none), rounded and capped at 100, computed only by `lib/exam/scoring.ts` on the server; the response also stores `rawPercent`, `correctCount` and `pointsMultiplier`. `firestore.rules` in the repo is the **final** ruleset (P5.5): the browser can only read/update its own profile and activity log, and admins can run the admin screens; quizzes, questions, attempts and results are server-only (results are readable by their owner, never writable). It is **deployed** (2026-10-26) and any change to it must be deployed again with `firebase deploy --only firestore:rules --project ageno-quiz-af3ff` (test it first: `__tests__/firestore-rules.test.ts`). Before relying on it, a new player-facing screen must get its data from a server route, not from Firestore: the rules deny the browser everything except a person's own profile and activity log.

### Site shell and design system

- Pages never render a header or footer. `components/layout/SiteFrame.tsx` (header, the single `<main id="main-content">`, optional footer) is used by the `(auth)`, `(quiz)`, `(user)` and `(public)` layouts. `(admin)` has its own layout. Don't put `<main>` in a page.
- Tokens live in `app/theme.css` (Agenoverse port) and brand utilities in `app/globals.css`. The default Tailwind palette still exists until P7.6, and `<body>` is still light. New or redesigned screens sit on a dark surface (`data-theme="dark"` + `bg-bg text-text`) and use token classes (`bg-surface`, `text-text-muted`, `border-border`, `text-accent`), not `gray-*`/`indigo-*`.
- Primitives are in `components/ui/` (import from `@/components/ui`); use `cn()` from `lib/utils.ts`. Don't add a component library.

### Large files to know about

- **The quiz-taking flow.** `app/(quiz)/q/[id]/client.tsx` (~270 lines) only wires things together: `hooks/useQuizLoader.ts` (one request: the public quiz plus question *counts* per level) → lobby (`components/quiz/lobby/`) or `ResumeAttempt` → `components/quiz/exam/QuizAttempt` (one attempt: `ExamShell`, `QuestionView`, `QuestionNavigator`, `SubmitDialog`, then `ResultsView`). Start/Resume/Retry call the attempt routes through `lib/exam/api.ts` (Bearer ID token; **no guests**: every attempt route needs sign-in, and the lobby's access-code field is just forwarded to the server, which checks it on start) and turn the answer into a seed with `lib/exam/seed.ts` (corrects the server clock against the device clock). Server side: `lib/server/attempts.ts` (`startAttempt`, `getAttempt`, `saveProgress`, `submitAttempt`; Firestore `attempts/{id}` holds a snapshot of the questions with their key, the deadline, answers, flags and counters, readable only through the Admin SDK) and `lib/server/request.ts`. A submit runs in one transaction (exactly once; a repeat returns the stored result), writes `responses/{attemptId}` + `answers/{questionId}`, and a submit later than deadline + 30s is not read: the last autosave counts and the result says `late`. Integrity signals (tab hidden, window blur, left fullscreen) are numbered **events** the browser reports with the autosave and the submit; `lib/exam/integrity.ts` `applyEvents` stamps them with the server's time, ignores repeats by `seq`, and derives the counts from them (a count sent by the browser is ignored). They end up on the response (`tabSwitchCount`, `blurCount`, `fullscreenExits`, `integrityEvents`). State for an attempt (answers, flags, submit guard, autosave to the device under `ageno:quiz:attempt:<quizId>:<uid>` and, debounced, to the server) is in `hooks/useQuizAttempt.ts`; pure helpers are in `lib/exam/` (`normalize.ts`, `scoring.ts`, `integrity.ts`, `answers.ts`, `storage.ts`). Mount `QuizAttempt` with `key={attemptId}`: a retry is a new attempt. `Quiz.examMode` (`practice` default, `strict`) decides what leaving fullscreen does (`FullscreenNotice` vs `FullscreenGate`, exits counted in `fullscreenExits`); Start/Resume/Retry request fullscreen from the click (`lib/exam/fullscreen.ts`). While an attempt runs, `useExamMode` (`components/layout/QuizFrame.tsx`) removes the site header.
- `components/admin/quiz-editor/`: the one admin quiz editor (create and edit), on `editor-state.ts` (reducer) and the shared schema; `components/admin/AdminPage.tsx` frames the admin pages.
- `lib/admin-analytics.ts` (score and time bands, report summary, CSV with formula-safe cells) feeds the admin dashboard and reports; charts are `components/admin/DistributionChart.tsx` (plain bars, no chart library). `lib/leaderboard.ts` ranks by the stored (already weighted) score; overall points = sum of each person's best score per quiz.

### Build config

`vercel.json` pins functions to `fra1`, next to Firestore (`eur3`); change both together. API routes add a `Server-Timing` header (`lib/server/timing.ts`) for finding slow steps in the Network tab. `<SpeedInsights />` is in the root layout.


`next.config.mjs` adds webpack aliases/fallbacks and `ProvidePlugin` for Node core modules (`process`, `buffer`, `stream`, `crypto`, etc.) on the client bundle, via the `*-browserify` devDependencies. Don't remove these without checking that the client build still works. Remote images are allowed only from `firebasestorage.googleapis.com`.
